## 1. 프로젝트 개요

SKN31 1기 1차 팀 프로젝트로, **F1 그랑프리(FIA Formula One World Championship)** 의 드라이버·팀 통계를 1950년부터 2026년까지 통합하여 동적 웹 대시보드로 제공하는 서비스다. F1 공식 홈페이지는 기본적인 성적 조회만 지원할 뿐 전체 기간 비교나 맞춤형 시각화 기능이 없다. 이 공백을 채우는 것이 기획의 출발점이었다.

4명(팀명: Team F4)이 이틀 안에 기획·설계·개발·산출물 작성 전 과정을 마쳐야 했다. 나는 **DB 설계(ERD)** 와 **드라이버 순위 페이지 구현**을 단독 담당했다.

## 3. 데이터 수집 전략

76년치 데이터를 하나의 DB로 통합하기 위해 세 가지 수집 방법을 병행했다.

- **Kaggle Dataset**: 1950~2024년 드라이버 성적, 컨스트럭터, 레이스, 서킷 정보 기반 데이터
- **F1 공식 사이트 웹 크롤링**: 2024~2026년 최신 경기 결과 (requests + BeautifulSoup)
- **Open API**: 시즌별 우승 횟수 및 드라이버 통계 보완

소스가 세 개다 보니 드라이버 이름 표기와 데이터 형식이 일치하지 않는 경우가 많았다. 포인트 컬럼은 `float`으로 통일하고, 날짜는 `YYYY-MM-DD` 형식으로 표준화했으며, 이름·팀명 표기 불일치는 수동 매핑으로 해소했다. 전처리가 분석의 기초라는 걸 이번에 제대로 체감했다.

## 4. DB 설계 (ERD)

6개 테이블의 관계를 dbdiagram.io로 모델링했다. 드라이버·팀·레이스·서킷이라는 도메인 개념을 어떻게 데이터 구조로 추상화할지 고민하는 과정이 가장 오래 걸렸다.

```
drivers_master  ──(driver_id)──►  driver_standings
constructors    ──(team_id)────►  driver_standings
constructors    ──(constructors_id)──►  constructors_standing
circuits        ──(circuit_id)──►  races
```

**주요 설계 판단**: `driver_standings`에 `first_name / last_name`을 비정규화하여 캐싱했다. 매 조회마다 `JOIN`을 걸면 성능 부담이 생기는 단순 이름 표시용 컬럼이었기 때문에, 이 경우에 한해 정규화 원칙보다 조회 편의를 우선했다.

## 5. 드라이버 순위 페이지 구현

내가 단독으로 설계·구현한 페이지다. MySQL에서 드라이버 성적 데이터를 조회하여 Streamlit으로 시각화한다.

### 핵심 기능

| 기능 | 동작 |
|------|------|
| 시즌 필터 | 연도 드롭다운 → '조회하기' 클릭 → 해당 시즌 성적 표시 |
| 이름 검색 | 이름 입력 → 매칭 드라이버 필터링, 결과 없을 시 별도 안내 화면 |
| 팀 필터 | 팀 드롭다운 → 팀별 목록 + 국적 분포 차트 + 포인트 시각화 |
| 초기화 | 전체 필터 리셋 → 기본 화면 복원 |

### 구현 시 고민한 것들

**동적 SQL WHERE 절 구성**: 시즌·이름·팀 세 필터가 동시에 적용될 수 있어, 선택된 조건만 WHERE 절에 추가되는 방식으로 쿼리를 동적으로 구성했다. 조건 수가 늘어나도 코드 구조가 무너지지 않도록 함수 단위로 분리하고 독스트링을 작성했다.

**빈 결과 핸들링**: 검색 결과가 없을 때 그냥 빈 테이블을 보여주는 게 아니라 명확한 안내 화면을 별도 렌더링했다. 사용자 입장에서 "데이터가 없는 건지, 오류인 건지" 모르는 상태가 가장 나쁜 UX라고 판단했다.

**Streamlit `session_state` 활용**: 필터 값이 페이지 리렌더링 시마다 초기화되는 Streamlit의 특성 때문에 `session_state`로 상태를 관리했다. 프론트엔드와 백엔드 사이의 데이터 흐름을 직접 다뤄본 첫 경험이었다.

## 7. 회고

이틀이라는 시간 제약이 오히려 집중력을 만들어줬다. 기획, 데이터 수집, DB 설계, 구현, 산출물 작성을 병렬로 돌려야 했기 때문에 각자의 작업이 다른 팀원의 작업을 블로킹하지 않도록 인터페이스를 먼저 합의하고 시작했다. ERD를 먼저 확정하고 각 페이지 개발이 시작된 것도 그런 이유였다.

기술적으로는 세 가지를 가져갔다.

**데이터 전처리의 무게감**: 소스가 다르면 같은 드라이버도 이름이 다르게 표기된다. 이걸 코드로 자동화하려다 결국 수동 매핑이 더 빠르다고 판단한 순간이 있었다. 완전 자동화가 항상 정답은 아니라는 걸 배웠다.

**ERD 설계의 논리적 쾌감**: 도메인 개념을 테이블 관계로 풀어내는 작업이 생각보다 재밌었다. 정규화를 언제 깰 것인지 판단하는 게 설계의 핵심이라는 것도 이번에 처음 실감했다.

**독스트링 습관**: 함수 작성할 때 입출력과 역할을 먼저 정리하고 코드를 짜는 흐름이 자연스럽게 생겼다. 빠르게 짠 코드를 다음 날 내가 알아보지 못하면 의미가 없다.

향후 개선하고 싶은 건 **실시간 데이터 갱신 파이프라인**이다. 현재는 크롤링 시점의 스냅샷이라 경기 후 수동 업데이트가 필요하다. APScheduler 같은 스케줄러로 자동 갱신 구조를 붙이면 진짜 서비스 수준으로 올라갈 수 있다.
