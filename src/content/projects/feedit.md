## 1. 프로젝트 개요

### 서비스 소개

**FEEDiT**은 흩어진 패션 데이터를 모으고(**FEED**), 정제해 트렌드의 온도를 읽는(**EDIT**) 패션 트렌드 분석 플랫폼이다. 커머스 · 리세일 · 콘텐츠 · 검색에 흩어진 신호를 하나의 패션 어휘 체계로 묶어 지표로 만들고, 그 결과를 **트렌드 분석 대시보드, AI 챗봇, 살!말? 구매 판단**으로 연결한다.

- 무신사 · 지그재그 · 에이블리(커머스), 무신사 유즈드 · KREAM(리세일), YouTube(콘텐츠), 네이버 · 구글(검색)에서 데이터를 수집하고, 약 3,000개의 패션 어휘 사전으로 정규화해 **0–100 트렌드 온도**를 포함한 6종 지표로 가공한다.
- 사용자는 트렌드 분석(FEED · EDIT), 일반 · 살!말? 두 모드의 AI 챗봇, 살!말? 커뮤니티 투표, 가상 피팅으로 **트렌드 탐색에서 구매 판단까지** 한 서비스 안에서 이어간다.
- 지표 · 가격 · 상품 URL은 모델이 만들지 않고 데이터 도구의 결과만 쓴다. 근거가 없는 부분은 비워 두고 "측정 자료 없음"으로 표시한다.

## 2. 프로젝트 기획

### 2.1 문제 정의

![FEEDiT을 만들게 된 이유](/images/projects/feedit/why-background.jpg)

**① 트렌드의 수명이 짧아졌다**

숏폼과 알고리즘 기반 확산으로 유행 주기가 빠르게 짧아지고 있다. 크로플(2020–2021)의 트렌드 반감기는 163일이었지만 두바이 초콜릿(2024)은 13일에 불과했다. 패션도 마찬가지로, 지그재그에서는 란제리 코어 관련 검색량이 20배, 거래액이 134배 급증하는 초단기 트렌드가 나타났다. 트렌드를 포착하는 타이밍이 곧 매출을 결정하는 구조가 됐다.

**② 정보는 많은데 판단이 어렵다**

인스타그램 · 유튜브에서 스타일을 발견하고, 무신사 · 지그재그에서 상품과 가격을 찾고, 후기 · 리뷰 · 댓글을 다시 확인한 뒤에야 살지 말지를 정한다. 발견 → 탐색 → 검증 → 판단이 한 곳에서 이어지지 않는다. 온라인 장바구니 이탈률은 **70.19%**, 소비자의 **62%** 는 가격 비교를 위해 구매를 보류한다. 소비자에게 정보가 없는 게 아니라, 너무 많아서 판단을 못 하는 것이다.

**③ 같은 상품도 플랫폼마다 표현이 다르다**

"오버핏 울 브이넥 니트", "루즈핏 V넥 니트 탑", "여리핏 브이넥 울 스웨터"처럼 같은 옷도 플랫폼마다 이름 · 카테고리 · 코드가 달라 같은 기준으로 비교하기 어렵다. 데이터를 모으기만 해서는 트렌드가 보이지 않는다.

그래서 **흩어진 신호를 수집하고, 하나의 공통 언어로 연결해, 발견에서 질문과 판단으로 이어지는 서비스**를 목표로 잡았다.

- 주요 비용은 LLM API 호출, AWS 서버 · 스토리지, 크롤링 운영이다.

2026년 9월 1일 기준 브랜드 3,000개 이상, 상품 10,000개 이상, 크리에이터 40명 이상의 초기 데이터 풀을 구축했다.

**① 수집 원칙**

- `robots.txt`를 받지 못하거나 차단된 경로는 자동 수집하지 않는다(fail-closed). 인증 · CAPTCHA 우회는 하지 않는다.
- 원문 · 이미지 · 자막 · 댓글은 내부 분석용으로만 쓰고 재배포하지 않는다. 작성자 식별정보 대신 해시 · 플랫폼 ID를 쓴다.
- 패션 크리에이터의 "살까 말까" 콘텐츠를 콘텐츠 신호의 중심으로 삼았다. 구독자의 구매 고민에 크리에이터가 조언하는 형식이라, 조회수가 꾸준하고 댓글에 구매 의향이 직접 드러난다.

**② 관리자 페이지에서 수집을 운영한다**

![수집 원천에서 RDS까지 데이터 흐름](/images/projects/feedit/data-flow.jpg)

수집 대상 정의(플랫폼 · URL · 주기) → 원본 수집 → S3 원본 보존 → 정제 · 정규화 → DB 적재 흐름을 관리자 페이지 한 화면에서 관리한다. 관리자는 플랫폼별 수집을 켜고 끄고, 수집 실행(crawl run)별 성공 · 실패 이력과 수집 건수 · 오류 로그, 누락 · 중복 같은 데이터 품질 현황을 확인한다.

#### 3.2.2 DB 설계

![데이터 구성](/images/projects/feedit/data-structure.jpg)

원본 · 수집(L0) → 패션 사전(Dictionary) → 정규화(L1) → 분석 Serving(L2) → 사용자 서비스(APP) 순서로 계층을 나눴다.

| 계층 | 역할 | 주요 테이블 |
|------|------|------|
| L0 Raw · Collection | 수집 실행 · 원본 위치 · 재현성 | source, crawl_run, raw_document |
| Dictionary · Taxonomy | 표준 브랜드 · 카테고리 · 패션 용어와 별칭 · 관계 | brand, category, term, term_alias, term_relation, normalization_review |
| L1 Core | 정규화된 상품 · 영상 · 텍스트와 시점별 관측값 | product, product_source, product_snapshot, yt_video, yt_video_stat, text_document |
| L2 Serving | 반복 조회용 일별 지표 · 연관어 · 가격 | term_daily_metric, term_assoc_daily, product_price_daily |
| APP | 계정 · 취향 · 행동 · 투표 · 대화 | app_user, user_taste, user_event, vote_card, vote_ballot, chat_session |

- **원본은 S3, RDS에는 포인터만.** JSON · HTML · 자막 원본은 S3에 불변 객체로 두고, RDS에는 위치와 SHA-256 해시를 기록한다. 전처리 규칙이 바뀌어도 같은 원본으로 다시 처리할 수 있다.
- **Master와 Snapshot을 분리한다.** 상품 · 브랜드처럼 변하지 않는 정보는 Master, 가격 · 랭킹 · 조회수처럼 시간에 따라 변하는 값은 Snapshot에 쌓는다. 같은 상품을 수집할 때마다 중복 저장하지 않으면서 변화 방향과 속도를 시계열로 본다.
- **표기 차이는 alias로 흡수한다.** 플랫폼별 브랜드 · 카테고리 · 용어 표기는 alias 테이블에서 표준 ID로 연결하고, 같은 상품에 같은 용어를 같은 관계로 두 번 연결하지 않도록 복합 유일성 제약을 건다.
- **서비스 요청마다 원본을 재집계하지 않는다.** 일별 지표는 L2에 미리 계산해 두고 화면 · API · 챗봇이 같은 값을 읽는다.

#### 3.2.4 처리: YouTube 수집과 LLM 전처리

**① 수집**

- YouTube Data API v3로 채널의 업로드 재생목록 → 영상 상세(제목 · 설명 · 조회수 · 좋아요 · 댓글 수 · 길이) → 댓글 순서로 수집한다. 영상 통계는 날짜별 Snapshot으로 쌓아 콘텐츠가 얼마나 빠르게 확산되는지 본다.
- YouTube API는 쇼츠 여부를 알려주지 않아 영상 길이로 판별했다. 기준은 **180초**다. YouTube의 쇼츠 최대 길이이기도 하고, 실제 수집 데이터에서 181–300초 구간이 비어 있어 쇼츠와 일반 영상이 명확히 갈렸다. 길이 원본을 함께 저장해 기준이 바뀌어도 재수집 없이 다시 분류할 수 있게 했다.

**② LLM 전처리: 댓글 · 영상 설명을 구조화한다**

댓글과 리뷰는 짧고, 반어와 줄임말이 많고, 칭찬의 대상이 옷인지 크리에이터인지도 섞여 있다. 키워드 빈도만 세면 "언니 오늘 너무 예뻐요"도 긍정 반응으로 잡힌다. 그래서 **사전 필터 → LLM 구조화 출력 → 코드 검증** 3단계로 처리했다.

| 단계 | 처리 |
|------|------|
| 1차 사전 필터 | 패션 사전 용어가 하나도 없는 문서는 LLM에 보내지 않고 잡담으로 처리해 토큰 비용을 줄인다 |
| 2차 LLM 분석 | 문서마다 대상(target) · 의도(intent) · 사전 용어 언급(mentions) · 사전 밖 후보(candidates)를 JSON Schema(strict) 구조화 출력으로 받는다 |
| 3차 근거 검증 | LLM이 돌려준 근거 구절이 원문의 해당 위치와 정확히 일치하는지 코드로 확인하고, 맞지 않으면 그 언급을 버린다 |

| 필드 | 값 | 의미 |
|------|------|------|
| target | PRODUCT · CREATOR · OTHER | 칭찬이 크리에이터를 향하면 CREATOR, 옷 · 상품 · 브랜드를 향할 때만 PRODUCT |
| intent | QUESTION · PRAISE · CRITIQUE · PURCHASE · EXPERIENCE · CHITCHAT | "비싸서 못 산다", "품절이라 아쉽다"는 구매 수요로 본다 |
| mentions | term · surface · slot · evidence_quote · 위치 · polarity · confidence | 사전 표준어, 원문 표기, 7개 슬롯(스타일 · 아이템 · 소재 · 디테일 · 컬러 · TPO · 브랜드), 판단 근거 구절 |
| candidates | 사전 밖 패션 표현 + 원문 근거 | 사전 확장 후보 |

- 영상 제목 · 설명은 크리에이터가 쓴 본문(`creator_content`)으로 따로 구분해, 크리에이터가 소개 · 추천하는 옷은 PRODUCT · PRAISE로 본다. 협찬 · 링크 · 채널 안내 문구는 무시한다.
- 문서 본문은 비신뢰 데이터로 다룬다. 댓글 안에 들어 있는 명령이나 출력 형식 변경 요구는 따르지 않도록 프롬프트에 명시했다.
- 결과는 문서의 분석 메타데이터(JSONB)에 의도 · 대상 · 언급 · 후보 · 감성 점수로 저장하고, 용어별 언급은 별도 행으로 적재해 일별 지표 계산에 바로 쓴다. 분석 모델과 프롬프트 버전도 함께 기록해 재분석 · 재현이 가능하다.

#### 3.2.5 처리: 검색량 지표

네이버 데이터랩과 Google Trends는 **0–100 상대값**만 준다. 기간 안에서 가장 많이 검색된 시점이 100이라, 이 값만으로는 키워드끼리도, 수집 시점끼리도 비교할 수 없다. 반면 네이버 검색광고 API와 Google Keyword Planner는 **월간 절대 검색량**을 준다. 그래서 두 값을 결합해 상대값을 절대 검색량으로 바꿨다.

**① 기준 키워드를 고른다**

절대 검색량을 알면서 데이터랩에서도 충분한 상대값을 가진 키워드를 기준 키워드 A로 삼는다. 후보 중 `평균 상대값 × 월간 절대 검색량`이 가장 큰 키워드를 고른다. 둘 다 클수록 비율 환산의 오차가 작다.

**② 비율로 환산한다**

```
B의 추정 절대 검색량 = (B의 상대값 ÷ A의 상대값) × A의 월간 절대 검색량
```

Google Trends도 같은 방식으로 Keyword Planner의 절대값을 기준으로 환산한다. 결과에는 기준 키워드와 환산 방식을 함께 기록해, 환산하지 못한 값은 환산하지 못했다고 남긴다.

**③ 지표에 반영한다**

패션 사전에서 키워드를 불러와 수집 → 원본 저장 → 환산 → 결과 저장 순서로 처리하고, 관리 명령으로 RDS에 적재한다. 검색량은 월 단위 신호라 일별 언급 수에 더하지 않고, 플랫폼 · 월 안에서 백분위로 정규화한 뒤 트렌드 온도의 관심(Attention) · 구매 의향(Intent) 축에 섞는다.

```python
def _find_reference_keyword(self, datalab_results):
    """검색광고 API로 절대 검색량을 알고, 데이터랩에서도 ratio가 충분한 키워드를 기준으로 삼는다."""
    best_ref, best_score = None, 0
    for result in datalab_results:
        keyword = result.get("title", "")
        if keyword not in self._reference_volumes:
            continue
        ratios = [d["ratio"] for d in result.get("data", []) if d.get("ratio", 0) > 0]
        if not ratios:
            continue
        avg_ratio = sum(ratios) / len(ratios)
        total_volume = self._reference_volumes[keyword]["total"]
        score = avg_ratio * total_volume          # 둘 다 높을수록 좋은 기준 키워드
        if score > best_score:
            best_score, best_ref = score, (keyword, avg_ratio, total_volume)
    return best_ref


def normalize_naver_datalab(self, datalab_data):
    results_data = datalab_data.get("data", [])
    ref = self._find_reference_keyword(results_data)
    normalized = []
    for result in results_data:
        for point in result.get("data", []):
            ratio = point.get("ratio", 0)
            estimated_volume, ref_keyword, method = None, None, "none"
            if ref and ratio > 0:
                ref_keyword, ref_ratio, ref_volume = ref
                if ref_ratio > 0:
                    # 핵심 치환 공식
                    estimated_volume = int((ratio / ref_ratio) * ref_volume)
                    method = "searchad_ratio"
            normalized.append({
                "keyword": result.get("title", ""), "platform": "naver",
                "period": point.get("period", ""), "ratio": ratio,
                "estimated_volume": estimated_volume,
                "reference_keyword": ref_keyword, "normalization_method": method,
            })
    return normalized
```

**① 트렌드 온도**

"트렌드"라는 추상적인 개념을 바로 이해할 수 있게 **0–100 온도**로 표현했다.

```
트렌드 온도 = 0.6 × Level + 0.4 × Momentum
Level      = 존재감 35% + 관심 30% + 반응 20% + 구매 의향 15%
```

| 축 | 가중치 | 신호 |
|------|:---:|------|
| 존재감 (Presence) | 35% | 상품 수, 랭킹 진입 상품 수, 콘텐츠 수, 크리에이터 수, 언급 수 |
| 관심 (Attention) | 30% | 상품 · 콘텐츠 조회수, 리뷰 수, 언급 수, 검색량 |
| 반응 (Engagement) | 20% | 좋아요, 댓글, 리뷰, 긍정 · 칭찬 비율 |
| 구매 의향 (Intent) | 15% | 구매 · 질문 의도 비율, 찜 · 구매 · 판매 수, 검색량 |

- **같은 기준으로 비교한다.** 플랫폼마다 데이터 규모가 달라 원시 수치를 곧바로 더하면 큰 플랫폼이 온도를 정해버린다. 그래서 각 신호를 같은 출처 안에서 **최근 28일 분포 대비 백분위**로 정규화한 뒤 의미 축으로 합친다. 축 가중치는 의미의 가중치일 뿐, 플랫폼 규모를 보정하는 값이 아니다.
- **Momentum은 관심이 커지는 속도다.** 최근 7일 평균과 28일 평균을 비교해, 같으면 50, 빨라질수록 100에 가까워지는 로지스틱 점수로 바꾼다.
- **없는 데이터를 0으로 채우지 않는다.** `0`은 실제로 관측된 0이고, 관측이 없으면 `None`이다. 관측된 신호의 가중치만으로 재정규화하고, 관측 범위(coverage)는 점수를 깎는 데 쓰지 않고 함께 표시한다.
- **극단적인 반응률을 완화한다.** 댓글 몇 개로 긍정률 100%가 나오지 않도록, 표본이 적은 반응률은 전체 분포 쪽으로 당겨서(Empirical-Bayes 축소) 계산한다.

```python
# 의미 가중치. 플랫폼 데이터 규모를 보정하는 값이 아니다.
LEVEL_WEIGHTS = {"presence": 0.35, "attention": 0.30, "engagement": 0.20, "intent": 0.15}
TEMPERATURE_WEIGHTS = {"level": 0.60, "momentum": 0.40}
NORMALIZATION_WINDOW_DAYS = 28
REACTION_PRIOR_STRENGTH = 5.0       # Empirical-Bayes 반응률 축소 강도


def available_weighted_mean(values, weights):
    """관측된 값의 가중치만으로 평균을 낸다. 없는 축은 0이 아니라 분모에서 빠진다."""
    pairs = [(float(values[k]), float(w)) for k, w in weights.items()
             if values.get(k) is not None and float(w) > 0]
    if not pairs:
        return None
    return sum(v * w for v, w in pairs) / sum(w for _, w in pairs)


def momentum_score(ma7, ma28):
    """7일·28일 평균이 같으면 50, 증가할수록 100에 가까운 로지스틱 점수."""
    ma7, ma28 = float(ma7 or 0), float(ma28 or 0)
    if ma28 <= 0:
        return 50.0 if ma7 <= 0 else 100.0
    return clamp(100.0 / (1.0 + exp(-6.0 * (ma7 / ma28 - 1.0))))
```

#### 3.3.2 챗봇 일반 모드: 필요한 도구를 골라 근거를 연결한다

![일반 챗봇의 작동 흐름](/images/projects/feedit/chatbot-general.jpg)

고정된 의도 분류 → 템플릿 매핑 대신, **오케스트레이터가 매 바퀴 다음에 부를 도구를 고르고 결과를 본 뒤 다시 판단하는 도구 호출 루프**로 만들었다. 근거를 보기 전에 질문의 의도를 확정하지 않기 위해서다.

1. **사전 게이트**: 질문 속 표현을 스타일 · 소재 · 아이템 · 브랜드 4축 사전과 대조해 조회 가능한 용어인지 먼저 가른다. 사전에 없는 표현에는 후보와 등재 요청을 제공한다.
2. **도구 선택**: 오케스트레이터가 `search_terms`로 표준 표기를 확정한 뒤, 질문에 따라 필요한 도구를 바퀴마다 고른다.
3. **리포트 조합**: 조회가 끝나면 `compose_report`가 실제로 조회한 결과 모듈만 골라 12열 리포트 카드를 조합한다. 완성 템플릿을 고르는 게 아니라 모듈을 조합한다.
4. **검증 · 다듬기 · 전송**: 숫자를 원본과 대조하고 문장을 다듬은 뒤, SSE로 `status → text → report → actions → done` 순서로 흘려보낸다.

| 도구 | 역할 |
|------|------|
| `search_terms` | 질문 속 용어의 정확한 표기와 축 확정 |
| `get_metric` · `rank_terms` | 온도 · 모멘텀 · 연관어 · 플랫폼별 언급량 조회, 순위 비교 |
| `get_evidence` | 판단 근거가 되는 리뷰 · 댓글 · 영상 원문 인용 |
| `similar_terms` · `get_user_taste` | 유사 용어 추천, 로그인 사용자의 취향 가중치 |
| `season_fit` · `web_search` | 계절 적합도, 필요할 때만 웹 검색 (출처를 못 찾으면 화면에 올리지 않음) |

사진을 첨부하면 Vision이 먼저 사진을 해석해 요약 · 아이템 · 속성을 대화 맥락으로 넘긴다. 일반 모드는 코디 제안까지만 하고, 살말 지수와 가상 피팅 실행 도구는 갖지 않는다.

루프에는 네 가지 안전장치를 걸었다. **최대 4바퀴**(링크 질문 +1), **전체 시간 예산 17초**(링크 질문 +8초), **같은 도구를 같은 인자로 다시 부르는 호출 차단**, **도구 호출 원본 보관**(TraceLog). 예산이 바닥나면 모델을 다시 부르지 않고 지금까지 확보한 근거에서 직접 요약 문장을 만들어, 응답이 아예 끊기는 일을 막는다.

#### 3.3.3 챗봇 살!말? 모드: 확인한 신호만으로 판단의 근거를 만든다

![살!말? 챗봇의 작동 흐름](/images/projects/feedit/chatbot-salmal.jpg)

1. **상품 확인**: 상품 링크는 `inspect_product_link`가, 사진은 Vision이 상품명 · 브랜드 · 가격을 한 번 확인한다. 확인하지 못한 값은 짐작으로 채우지 않고 비워 둔다.
2. **5대 신호 병렬 조회**: 취향 · 행동 · 트렌드 · 가격 · 커뮤니티 신호를 각각의 데이터에서 동시에 가져온다.
3. **살말 지수 계산**: LLM이 아니라 **코드로 계산**한다.
4. **조언과 검증**: Terra가 점수와 근거로 한 줄 조언을 쓰되 지수 값 자체는 만들지 않고, 숫자와 근거를 다시 대조한다.
5. **결정 카드**: 점수 · 살/말/보류 · 신뢰도와 근거 · 결측 리포트, [지표로 보기] [물어보기] [입혀보기] 후속 행동을 준다.

```
살말 지수 = Σ(확인된 신호 점수 × 가중치) ÷ Σ(확인된 신호의 가중치)
```

| 신호 | 가중치 | 근거 데이터 |
|------|:---:|------|
| 취향 | 35% | 로그인 사용자가 즐겨 입는 스타일 · 대표 어휘와 상품 스타일의 일치 |
| 행동 | 25% | 최근 검색 · 찜 이력 |
| 트렌드 | 20% | 트렌드 온도 · 모멘텀 |
| 가격 | 15% | 현재 할인율 |
| 커뮤니티 | 5% | 살!말? 투표 비율 (참고 신호) |

- **67점 이상은 살, 43점 이하는 말**, 그 사이는 보류다.
- 없는 신호는 50점(중립)으로 채우지 않고 분모에서 뺀다. 확인된 가중치가 **40% 미만이면 점수와 관계없이 보류**로 고정하고, 75% 이상이면 신뢰도 높음, 50% 이상이면 보통으로 표시한다.
- 신호가 빠졌을 때는 **왜 빠졌는지**를 함께 준다. 로그인했는데 취향 신호가 빠지면 사용자는 로그인이 안 된 줄 안다. 실제로는 상품의 스타일을 몰라 비교할 대상이 없었던 경우라, 그 이유를 그대로 보여준다.

<details>
<summary>코드 보기: 살말 지수 계산</summary>

```python
WEIGHTS = {"taste": 35, "behavior": 25, "trend": 20, "price": 15, "community": 5}

available_weight = sum(WEIGHTS[k] for k in signals)        # 확인된 신호만
if not available_weight:
    return {"score": None, "recommendation": "판단 자료 부족", "confidence": "낮음", ...}

score = round(sum(v["score"] * WEIGHTS[k] for k, v in signals.items()) / available_weight)
coverage = round(available_weight / sum(WEIGHTS.values()) * 100)

if coverage < 40:
    recommendation, allowed = "보류", False      # 근거가 부족하면 점수와 관계없이 보류
elif score >= 67:
    recommendation, allowed = "살", True
elif score <= 43:
    recommendation, allowed = "말", True
else:
    recommendation, allowed = "보류", True
confidence = "높음" if coverage >= 75 else "보통" if coverage >= 50 else "낮음"
```

#### 3.3.4 숫자 검증 가드레일

이 프로젝트에서 가장 먼저 금지한 것은 **지어낸 숫자**다. 트렌드 온도 86점이 87점으로, 333건이 "300여 건"으로 바뀌는 순간 지표 서비스는 신뢰를 잃는다. 모델에게 "숫자는 바꾸지 마"라고 부탁하는 대신 구조로 막았다.

**① 숫자 봉인**

문장을 다듬기 전에 모든 숫자를 자리표시자로 바꿔 보낸다. 모델은 `⟦0⟧`이 무슨 값인지 모르기 때문에 바꿀 수 없다. 돌아온 문장에서 자리표시자가 그대로 있는지, 새 숫자가 생기지 않았는지, 태그 · 길이가 정상인지 확인하고, 하나라도 어긋나면 다듬기 전 원문을 그대로 쓴다. 다듬기는 있으면 좋은 것이지 없으면 안 되는 것이 아니다.

```
발레코어의 트렌드 온도는 86점 · 과열입니다.
→ 발레코어의 트렌드 온도는 ⟦0⟧점 · 과열입니다.
```

**② 원본 대조**

답변 속 숫자를 TraceLog에 보관한 도구 결과 원문과 기계적으로 대조한다. 이 단계는 모델을 부르지 않는다. 의심스러운 숫자가 있을 때만 경량 모델이 근거 없는 값을 지우거나 "측정 자료가 없습니다"로 고쳐 쓴다.

**③ 결측 명시**

최근 7 · 14 · 28일 관측이 각각 3 · 5 · 10건에 못 미치면 그 용어의 수준 · 방향 · 2주 변화에 대한 발언을 차례로 막고, 막힌 이유를 함께 준다. 조회한 용어가 전부 측정되지 않았어도 카드가 조용히 사라지지 않도록 결측 모듈로 남긴다.

**④ 장애 대응**

LLM 호출이 실패하면 규칙 기반 경로로 전환해 서비스가 계속 동작하고, 응답에 그 흔적을 남겨 원인을 추적한다. 가상 피팅이 실패해도 대화 흐름은 끊기지 않는다.

<details>
<summary>코드 보기: 숫자 봉인과 검증</summary>

```python
_NUM = re.compile(r"[-−+]?\d[\d,]*(?:\.\d+)?")   # '1,284' · '86' · '3.88' · '−12'를 통째로
_PH = "⟦{}⟧"
_PH_RE = re.compile(r"⟦(\d+)⟧")


def seal(text):
    """숫자를 자리표시자로 바꾼다."""
    vals = []
    def sub(m):
        vals.append(m.group(0))
        return _PH.format(len(vals) - 1)
    return _NUM.sub(sub, text), vals


def verify(sealed_in, sealed_out, vals):
    """다듬은 문장을 받아도 되나. 안 되면 이유를 돌려준다 (None이면 통과)."""
    if not sealed_out or not sealed_out.strip():
        return "EMPTY"
    want = sorted(int(m) for m in _PH_RE.findall(sealed_in))
    got = sorted(int(m) for m in _PH_RE.findall(sealed_out))
    if want != got:
        return f"PLACEHOLDER_MISMATCH {want} != {got}"
    if re.search(r"\d", _PH_RE.sub("", sealed_out)):   # 자리표시자 밖에 숫자가 새로 생겼나
        return "NEW_DIGIT"
    if len(sealed_out) > len(sealed_in) * 1.6 + 20:
        return "TOO_LONG"
    return None
```

</details>

#### 3.3.5 스타일 분류기

![스타일 분류기의 문제와 해결 방안](/images/projects/feedit/classifier-approach.jpg)

트렌드를 보려면 스타일이 가장 중요한 키워드인데, 텍스트 전처리로 상품마다 스타일을 붙이려 해도 **라벨 없는 상품 이미지가 4,000장 넘게** 남았다. 상품명만으로는 스타일을 알 수 없는 경우가 많았기 때문이다.

- 처음에는 멘토 자문을 받아 **CLIP 기반 zero-shot**으로 분류했다. 옷 사진과 스타일 설명 프롬프트를 주면 프롬프트를 기준으로 분류하는 방식이라 학습이 필요 없었지만, 결과가 우리 데이터의 라벨과 맞지 않았다. 영문 프롬프트 기반이라 한국 패션 스타일 구분이 약했다.
- 그래서 **지도학습으로 전환**했다. 베이스 모델은 OpenCLIP → Marqo → **ZooClaw-FashionSigLIP2**로, 분류기는 MLP · SVM · LightGBM을 거쳐 **Linear Probe**로 정했다. 이미지 인코더는 고정하고 768차원 임베딩 위에 선형 분류기만 학습하는 구조다.
- 학습 데이터는 무신사 스타일 태그를 시드로 상품 이미지를 모은 뒤, 자동 태그만으로는 클래스 경계가 부정확하고 편향돼 **수동으로 교정**했다. 뒷모습 · 얼굴 · 액세서리 컷 같은 노이즈 이미지는 제거하고 부족한 클래스를 보충해 **14종 스타일, 5,142장**을 만들었다.

![5,142장의 패션 이미지 데이터](/images/projects/feedit/classifier-data.jpg)

t-SNE로 임베딩을 2차원에 펼쳐 보면 수동 태깅 후 스타일별로 군집이 형성된다. 다만 완전히 분리되지는 않는다. 바람막이는 스포츠로도, 스트릿으로도 입을 수 있기 때문이다. 최종 모델은 ZooClaw-FashionSigLIP2 + Linear Probe v4로, 약 81%의 정확도로 채택했다.

#### 3.4.3 배포와 서비스 테스트

프론트엔드는 Vercel, API 서버와 챗봇 서버는 AWS EC2의 Docker 컨테이너로 배포했고, nginx가 HTTPS를 종료하고 SSE 버퍼링을 끈 채 요청을 나눈다. GitHub Actions가 PR과 `main` 반영 때마다 프론트 빌드 · 테스트, 챗봇 테스트, Django 마이그레이션 검사와 테스트를 돌린다.

서비스 테스트는 사용자 목적 기준의 시나리오 8개로 설계했다.

| ID | 시나리오 | 판정 기준 |
|------|------|------|
| SC-01 | 회원가입부터 재로그인까지 | 정상 가입 201 · 로그인 200 · 잘못된 비밀번호 401, 인증 전 가입과 CSRF 누락 요청 거절 |
| SC-02 | 트렌드 검색과 기간 전환 | 늦게 도착한 이전 요청이 최신 결과를 덮지 않고, 없는 데이터를 숫자로 채우지 않음 |
| SC-03 | 상품 탐색과 찜 관리 | 저장 실패 시 이전 상태와 오류 사유 유지 |
| SC-04 | 내 피드와 주간 리포트 | 사용자별 기록이 섞이지 않고 대화 이력이 복원됨 |
| SC-05 | 근거를 확인하는 AI 대화 | SSE 블록이 누락 없이 UI로 연결되고, 근거 없는 수치를 분석 결과처럼 표시하지 않음 |
| SC-06 | 살!말? 판단에서 가상 피팅으로 이동 | 모드별 허용 도구를 지키고, 생성 실패를 성공 이미지처럼 표시하지 않음 |
| SC-07 | 운영자의 품질 점검과 신고 처리 | DB 집계와 화면 표시가 일치하고, 운영자 외 접근은 거절 |
| SC-08 | 탈퇴 후 개인정보와 사본 정리 | 본인 식별정보 · 원문 사본은 정리되고, 필요한 신고 기록과 다른 사람의 게시물은 유지 |

### 4.1 평가

HTTP 200이나 서버의 완료 표시를 품질과 같은 것으로 보지 않고, 응답 품질 결함은 별도로 기록했다. 자동 실행 결과와 운영 환경 확인 결과도 나눠서 적었다.

#### 4.1.1 서비스 테스트

### 4.3 회고 · 향후 계획

- **트렌드 온도는 수식보다 데이터 구조의 문제였다.** 플랫폼마다 데이터 규모가 달라 원시 수치를 그대로 합치면 규모가 큰 플랫폼이 온도를 좌우한다. 출처별로 28일 분포 안에서 정규화한 뒤 의미 축(존재감 · 관심 · 반응 · 구매 의향)으로 합치는 구조로 정리하고 나서야, 서로 다른 플랫폼의 신호를 같은 온도로 읽을 수 있었다.
- **모델이 숫자를 만들 수 없게 하는 것이 가장 확실한 신뢰 장치였다.** 다듬어 달라고만 해도 모델은 숫자를 바꿨다. 그래서 부탁하는 대신 숫자를 봉인하고, 살말 지수는 LLM이 아닌 계산기로 만들고, 답변 속 숫자는 도구 결과 원본과 대조했다.
- **모른다고 말하는 것도 기능이다.** 없는 데이터를 0이나 50으로 채우지 않고 분모에서 빼고, 근거가 부족하면 결론을 보류했다. 그럴듯한 점수보다 "측정 자료 없음"이 사용자의 판단에 더 정직한 정보였다.
- **어휘 사전이 모든 단계의 공통 언어였다.** 정규화, 지표 계산, 질문 해석, 스타일 분류가 모두 같은 사전을 기준으로 움직였기 때문에, 사전의 품질이 곧 서비스 전체의 품질이었다. 사전 밖 표현을 버리지 않고 후보로 남긴 것도 그래서다.

| 다음 단계 | 내용 |
|------|------|
| 지표 검증 | 시장 지표 교차 검증, 시간 분할 검증, 편향 · 실패 사례 점검을 실제 데이터로 수행 |
| 다국어 지원 | 질문과 응답을 한국어 · 영어 · 일본어로, 언어가 달라도 같은 데이터 근거로 답하도록 확장 |
| 파트너 연결 | 커머스(상품 연동 · 구매 접점), 스타일리스트(개인별 컨설팅), 인플루언서(크리에이터 협업)로 연결 |
