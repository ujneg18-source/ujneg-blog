## 1. 프로젝트 개요

보호자가 증상을 설명하면 VectorDB에 적재된 가이드라인을 근거로 안내하고, 거주 지역을 알려주면 가까운 치매안심센터의 위치·운영기관·제공 프로그램을 알려주는 챗봇이다. SK네트웍스 Family AI 캠프 3차 프로젝트로 만들고, 4차 프로젝트에서 팀원 4명이 서비스를 확장했다.

## 2. 배경

- 국내 치매 환자 수는 2026년 100만 명을 넘고, 2044년에는 200만 명을 넘어설 전망이다.
- 중앙치매센터 「2025년 치매 인식도 조사」에서 치매안심센터 인지도는 49.4%였지만, 실제 방문 경험률은 12.1%에 그쳤다.
- 국민이 가장 필요로 하는 정보는 예방 및 치료(76.2%), 원인 및 증상(49.9%) 순이었다.

센터가 있다는 건 알아도 실제로 가지는 않는다. 그래서 **초기 증상 정보에 쉽게 닿고, 그 대화가 가까운 센터로 자연스럽게 이어지는 챗봇**을 기획했다.

## 3. 구조

LangGraph 기반 ReAct 에이전트가 질문 내용에 따라 GraphDB와 VectorDB 중 어떤 도구를 쓸지 스스로 판단한다. 정해진 순서대로 흐르는 체인 대신, LLM과 도구가 답이 나올 때까지 왕복하는 루프를 썼다.

1. 생각 — 질문에 필요한 정보가 무엇인지 판단
2. 행동 — GraphDB / VectorDB 도구 호출
3. 관찰 — 결과 확인
4. 재판단 — 더 필요하면 1번으로
5. 최종 답변

| 저장소 | 담는 것 |
|------|------|
| GraphDB (Neo4j AuraDB) | 시도 → 시군구 → 치매안심센터 → 운영기관 → 프로그램 |
| VectorDB (Qdrant) | 치매 조기검진·증상 가이드라인 문서 |
| Supabase | 세션 단위 단기 상태, 사용자별 장기 상태 |

## 4. GraphDB 구축 (담당)

### 왜 GraphDB인가

"강남구에 치매안심센터 몇 개야?", "인지훈련 프로그램 하는 센터 어디야?", "삼성서울병원이 운영하는 센터는?"처럼 **지역 · 센터 · 운영기관 · 프로그램 사이의 다대다 관계**를 묻는 질문이 많았다. RDB라면 JOIN을 여러 번 거쳐야 하는 질문을, GraphDB는 관계를 그대로 따라가면 된다.

### 데이터: 공공데이터 2종 병합

| 데이터셋 | 규모 | 장점 | 한계 |
|------|------|------|------|
| ① 국립중앙의료원 치매안심센터 정보 | 256행 | 센터명·주소·위경도가 정제되어 있음 | 운영기관·프로그램 정보가 없음 |
| ② 전국치매센터표준데이터 | 317행 | 운영기관·인력·프로그램 정보가 있음 | 시도/시군구가 주소 문자열에 섞여 있음 |

한쪽만으로는 정제된 위치 정보와 프로그램 정보를 동시에 얻을 수 없어서, ①을 기준으로 ②의 정보를 매칭해 보강했다.

### 전처리에서 부딪힌 문제

| 문제 | 해결 |
|------|------|
| ②의 시도/시군구가 주소 문자열 안에 있음 | 주소 앞 토큰을 파싱해 별도 컬럼으로 분리하고 표기를 정규화 |
| 인력 현황이 자유 텍스트("임상심리사 1, 음악치료사 1") | 15개 내외 표준 직종으로 매핑 테이블을 만들어 정리 |
| 이름 표기 차이로 같은 센터가 두 번 들어감 ("광주서구안심센터" / "서구안심센터") | **전화번호 기준으로 중복 45개 그룹(약 90개 노드)을 찾아 병합** |
| 센터 홈페이지 결측 101건 | 전수 조사로 `nid.or.kr` 패턴과 지자체 공식 도메인을 수동 매핑. 운영기관 홈페이지 225건도 추가 조사 |
| URL에 `https://`가 빠진 값, 인원수가 float로 저장된 값 | 프로토콜 일괄 보완, 인원수·우편번호 int 변환 |

### 최종 그래프

| 노드 | 관계 |
|------|------|
| 시도 17 · 시군구 263 · 치매안심센터 313 · 운영기관 228 · 프로그램 683 | `LOCATED_IN` · `CONTAINS` · `MANAGES` · `PROVIDES` |
| **총 1,504개** | **총 2,419개** |

### 에이전트 도구 설계: 고정 Tool 9개 + Fallback 1개

LLM이 모든 질문을 직접 Cypher로 만들게 하면 쿼리 오류가 생기는 경우가 있었다. 그래서 **자주 나오는 질문은 미리 검증한 Cypher로 고정 Tool을 만들고**(시도·시군구별 센터, 운영기관, 프로그램 조회 등 9개), 고정 Tool로 처리되지 않는 복합 질문만 LLM이 Cypher를 생성하는 Fallback Tool 1개가 맡도록 나눴다.

## 5. 성능 평가

| 대상 | 방법 | 결과 |
|------|------|------|
| GraphDB | 고정 Tool 9개 + Fallback 1개에 질문 1개씩, 결과에 정답 키워드가 모두 들어있는지 확인 | Precision · Recall **1.0** (10/10) |
| VectorDB | 질문 10개에 대해 top-4 검색 결과에서 정답 키워드가 처음 나온 순위 측정 | Hit Rate **1.0** · MRR **0.93** |

Fallback으로 처리한 "의사가 2명 이상인 센터" 같은 속성 + 관계 결합 질문까지 정답을 반환했다.

검색 단계는 잘 동작했지만, RAGAS로 측정한 최종 답변 품질(Faithfulness 0.27, Answer Relevancy 0.41)은 낮게 나왔다. 검색한 근거를 답변에 충실히 반영하도록 프롬프트와 응답 구조를 다듬는 것이 다음 과제로 남았다.

## 6. 4차 프로젝트: 서비스 확장

4차 프로젝트에서는 상담 챗봇에 더해, 보호자가 매일 쓰는 서비스로 넓혔다. 이 단계의 PM은 다른 팀원이 맡았고, 나는 GraphDB · VectorDB 설계와 데이터 수집, 예방 정보 포스팅을 맡았다.

- **오늘의 대화**: 3~5턴 짧은 대화를 AI가 요약해 하루 한 번 기록하고, 상태에 따라 센터 찾기를 권한다.
- **두뇌 게임**: 스도쿠·카드 짝 맞추기 등 게임 기록과 통계
- **예방 정보**: 식습관·운동·수면 등 예방 콘텐츠
- **센터 지도**: 지도에서 가까운 치매안심센터 찾기
