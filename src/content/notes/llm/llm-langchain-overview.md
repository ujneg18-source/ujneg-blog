## LLM 개요

- **LLM**(Large Language Model, 대형 언어 모델)은 대량의 텍스트(최근에는 이미지·음성 등 멀티모달 데이터까지)에서 언어의 패턴을 학습해, 입력 문맥에 맞는 출력을 생성하는 AI 모델이다
  - 언어를 다루는 범용 두뇌 역할을 한다
  - '사실 DB'가 아니라 '언어 패턴'을 잘 맞추는 두뇌이기 때문에 **검증과 근거 설계**가 중요하다
- 대부분의 LLM은 **Transformer** 아키텍처에 기반하고, 층을 아주 많이 쌓은 큰 구조다
- 다양한 분야의 대량 데이터로 학습했기 때문에 특정 분야에 국한되지 않고 여러 작업에 바로 쓸 수 있다

```python
# ai-agent(prompt, data, rag, langchain ex.gpt,geminai,claude) <===> (LLM=엔진,동력,두뇌) 

# DL(LLM) => 대량의 텍스트에서 언어의 패턴을 학습해서, 대답을 함 

# large의 뜻
# 01 모델의크기 파라미터가 70억개(7B) 이상 
# 02 훈련데이터의 크기 4990억 토큰

# 멀티모달 => 대량의 텍스트, 이미지, 음성 등
```

```python
# llm -> 다음에 나올 확률 높은 단어를 맞추는 것 사실DB가 아니기에 검증/근거 설계가 필요하다
# llm -> hallucination 문제 -> ㅡ검증/근거
```

AI Agent를 자동차에 비유하면 LLM은 엔진이다. 프롬프트, 데이터, RAG, LangChain은 그 엔진을 원하는 방향으로 움직이게 하는 나머지 부품이다. 그리고 LLM이 하는 일은 결국 **다음에 올 확률이 높은 토큰을 고르는 것**이다. NLP 시리즈의 Transformer Decoder(GPT)가 하던 일과 같다. 그래서 그럴듯하지만 틀린 답(할루시네이션)이 나올 수 있고, 이 문제를 어떻게 다루느냐가 시리즈 전체를 관통한다.

## LLM 활용 방식의 변화

### 초기 (2022~2023): 프롬프트 엔지니어링

- 사용자가 질문하면 LLM이 답하는 서비스였다
- 그럴듯한 답변 생성이 주요 목표였다
- 원하는 응답을 얻고 할루시네이션을 줄이기 위해 **프롬프트 설계**가 중요했다
- 한 번의 호출로 끝나는 단발성 작업 중심이었다

```python
# 22-23 => 환각이 높았기 때문에 => 프롬포트 설계/엔지니어링이 중요
# 프롬프트 엔지니어링 (이제는 일반적인 능력)
# 단발성 => single turn / 현재도 llm 자체는 단발성임
```

"현재도 LLM 자체는 단발성"이라는 점이 중요하다. 모델 API는 지금도 요청 하나에 응답 하나를 돌려줄 뿐이고, 이전 대화를 기억하는 것처럼 보이는 건 애플리케이션이 대화 내역을 매번 다시 넣어 주기 때문이다. 이 부분이 뒤에 나오는 Memory다.

### 2024년: RAG와 추론 모델

- **RAG**(Retrieval-Augmented Generation)가 대중화되었다
- 수학, 코딩처럼 논리적 사고가 필요한 일에 특화된 **추론(Reasoning) 모델**이 등장했다 (2024년 12월 OpenAI o1 정식 출시)
- Agent 프레임워크와 워크플로우 기반 개발이 시작되었다
- 단순 프롬프트 설계보다 **시스템 설계**의 중요성이 커졌다

```python
# 23-24 환각을 줄이는 게 목적이 됌 => 'rag'가 대중화 됌. Q-A이라는 자연어의 한분야였음, 허깅페이스2(수업내용) => context & question 부분
# context(문서=검색)
# LLM의 능력 중 문서이해를 사용함.

# 문제는 user는 prompt를 시스템에 정확히 보내지 않음

# rag
# 우리문서에서 찾을수도 있고, 웹 검색을 하거나 등 (##시스템 상##에서 만들어야 함)

# 추론(o1)모델이 생김 = 어떻게 하면 답변을 잘할까.
```

허깅페이스 Pipeline 글의 질의응답 실습이 RAG의 뼈대였다. 문서(context)와 질문(question)을 프롬프트에 함께 넣고 문서 안에서 답을 찾게 했다. RAG는 여기서 **문서를 사람이 붙여 넣는 대신 시스템이 질문에 맞춰 검색해서 넣는** 구조다. 사용자는 프롬프트를 정확하게 써 주지 않으니, 그 부분을 시스템이 채운다.

RAG용 프롬프트는 이런 모양이다.

```python
# 다음에 나오는 <문서>의 내용을 바탕으로 <질문>에 대해서 답변해줘. 
# <문서>에 질문에 대해 참고할 내용이 없으면 "모른다" 라고 답해줘.

# <문서> => rag에선 사용자 질문에 맞춰서 이부분을 찾을거임

# 우리나라 2대 수출 품목인 자동차가 도널드 트럼프 미국 행정부의 관세 여파로 지난달 큰 폭의 수출 감소율을 보이면서 우려가 커지고 있다. (… 기사 본문 …)

# </문서>

# <질문>
# 짜장면 조리법을 알려줘.
# </질문>
```

자동차 관세 기사를 주고 짜장면 조리법을 묻는, 일부러 엇나간 예시다. 핵심은 둘째 줄의 **"참고할 내용이 없으면 '모른다'라고 답해줘"**다. 문서 밖의 질문에는 모델이 아는 지식으로 지어내지 말고 모른다고 하도록 막는 장치이고, 할루시네이션을 줄이는 가장 기본적인 방법이다.

```python
# 사용자가 프롬포트를 쓰면 시스템에서 수백줄의 프롬포트를 만들어서 llm에 보냄(2024의 가장 중요 hot) => 2025쯤 마무리 + 추론모델
```

### 2025년 이후: AI Agent

본격적인 AI Agent의 시대다. LLM을 단순 채팅 엔진이 아니라 **작업을 수행하는 실행 주체**로 쓰는 흐름이 강해졌다.

| 흐름 | 내용 |
|---|---|
| **도구 사용** (Tool Use / Function Calling) | 검색, DB 조회, 계산, API 호출 같은 외부 도구를 활용한다 |
| **Agent와 Workflow** | 여러 단계를 반복하거나 분기하면서 목표를 수행한다 |
| **장문 컨텍스트** (Long Context) | 100만 토큰 이상을 입력으로 받는 모델이 늘었다. 문서, 코드베이스, 로그를 통째로 분석한다 |
| **모델 선택** (Model Routing) | 속도, 비용, 추론 능력에 따라 여러 모델을 조합한다 |
| **관측성과 평가** (Observability, Evaluation) | 응답 품질뿐 아니라 처리 과정 전체를 추적·평가·모니터링한다 |
| **컨텍스트 엔지니어링** | 프롬프트 문장보다, 모델에 **어떤 정보를 어떤 방식으로** 제공하느냐가 중요해졌다 |

```python
# AI agent (추론모델의 등장으로 인함-사용자의 프롬포트(Question, problem)를 받으면 // [뇌(LLM)]에선 [추론모델-생각을 단계적]으로 만들어냄-

# LLM(뇌) -> 도구들로 보내서 일을 시킴

# LLM의 도구 (google, bing검색) LLM에 도구를 붙여줌 /도구를 통일 = mcp
# - (함수를 만들어줌/LLM이 함수를 호출해줌-Function 호출) 

# 입력토큰이 늘어남 

# 모델을 나눠서 조합함/ (저가or고가) 나눠서 일을 시킬 수 있음 (스스로 선택함)

# 프롬프트 엔지니어링 => 컨텍스트 엔지니어링(프롬프트 설계) / 하네스 엔지니어링(일을 시키는 방법)

# 관측성+평가

# 프롬프트설계=컨텍스트 엔지니어링=어디서 어떻게 물어볼것인지 

# vision check => 공장 (불량을 바로바로 check)
```

세 시기를 한 줄씩 줄이면 이렇다.

| 시기 | 핵심 질문 | 대표 기술 |
|---|---|---|
| 2022~2023 | 어떻게 **물어볼까** | 프롬프트 엔지니어링 |
| 2024 | 무엇을 **같이 줄까** | RAG, 추론 모델 |
| 2025~ | 무엇을 **하게 할까** | Tool Calling, Agent, MCP, 컨텍스트·하네스 엔지니어링 |

> **보충** MCP(Model Context Protocol)는 Anthropic이 2024년 11월 공개한 표준으로, LLM 애플리케이션이 외부 도구·데이터와 연결하는 방식을 통일한다. 메모의 "도구를 통일 = mcp"가 이 뜻이다. 도구마다 연결 코드를 따로 짜는 대신, MCP 서버로 만든 도구는 MCP를 지원하는 어느 애플리케이션에서나 쓸 수 있다.

## LLM의 주요 특징

### 대규모 모델과 대규모 데이터

LLM의 **Large**는 두 가지 의미다.

- **모델의 크기**: 수십억에서 수천억 개 이상의 파라미터를 가진다. 일반적으로 **70억(7B)** 개 이상이면 LLM으로 본다
- **학습 데이터의 규모**: 웹 문서, 책, 논문, 코드, 대화 데이터를 **토큰** 단위로 학습한다
  - 영어는 1토큰이 약 3~4글자(약 0.75단어), 한국어는 대략 1~2글자다. **한국어가 토큰을 더 많이 쓴다**

| 모델 | 파라미터 | 학습 토큰 |
|---|---|---|
| GPT-3 (2020) | 175B | 데이터셋 약 4,990억 |
| Meta Llama 3.1 | 8B / 70B / 405B | 약 15조 |
| DeepSeek-V3 | 671B (MoE, 토큰당 약 37B만 활성화) | 약 14.8조 |
| Qwen3 계열 | 0.6B ~ 235B | 약 36조 |
| GPT, Claude, Gemini | 비공개 | 비공개 |

영문 300쪽 책 한 권을 약 13만 토큰으로 치면, 15조 토큰은 책 1억 권 이상이다.

```python
# gpt 3.5는 하드웨어 환경이 되면 우리도 허깅페이스에서 받아서 돌릴 수 있음 
```

> **보충** GPT-3.5는 가중치가 공개되지 않은 상용 모델이라 Hugging Face에서 받을 수 없다. 하드웨어만 있으면 받아서 돌릴 수 있는 건 Llama, Qwen, Gemma 같은 **오픈소스(오픈 웨이트) 모델**이다. OpenAI도 2025년 8월 오픈 웨이트 모델(gpt-oss)을 따로 공개했는데, GPT-3.5와는 다른 모델이다.

```python
# 한글 토큰이 더 비쌈

# 시스템프롬프트는 영문으로 넣는게 좋음. (영어는 token 비용을 절감할 수 있음)

# LLM => 영어문서를 많이 학습함 
```

API 요금은 토큰 수로 매기기 때문에 같은 내용이라도 한국어가 더 비싸다. 매 요청마다 반복해서 들어가는 시스템 프롬프트를 영어로 쓰면 비용을 줄일 수 있고, 학습 데이터가 영어 위주라 지시를 더 잘 따르기도 한다.

### 자연어 생성과 이해, 다국어, 파운데이션 모델

- **자연어 생성과 이해**: 질문의 의도, 앞뒤 문맥, 지시사항, 예시를 참고해 응답을 만든다. 챗봇, 문서 작성, 요약, 번역, 코드 작성, 데이터 분석 보조에 쓰인다
- **다국어 지원**: 여러 언어를 함께 학습한 **다국어 모델**이다. 단, 언어별 성능은 같지 않다. 학습 데이터가 많은 영어가 가장 좋다
- **파운데이션 모델**: 특정 작업 하나가 아니라 다양한 작업의 **기반**으로 재사용한다. 하나의 LLM으로 챗봇, 검색 보조, 코딩 도우미, 고객 상담, 튜터를 만들 수 있다. 최근에는 이미지·음성·영상·문서까지 다루는 **멀티모달 파운데이션 모델**로 발전하고 있다

```python
# 톨스토이-작품을 학습시키면 그 작가처럼 말할수있음
# 파운데이션(범용)
```

```python
# 프롬프트를 완성할 때 초기에 바로 완성시킬 수 없음
# 출력물을보고 맘에 안드는것을 계속 추가해서 완성해야함
```

프롬프트는 한 번에 완성되지 않는다. 출력을 보고 마음에 안 드는 부분을 지시문에 추가하는 과정을 반복한다. 이 반복을 체계적으로 기록하고 비교하는 도구가 뒤에 나오는 LangSmith다.

## LLM의 한계

| 한계 | 내용 |
|---|---|
| **편향(Bias)** | 학습 데이터의 편향을 반영해 차별적 표현이나 정치적 편향이 나올 수 있다. 데이터 정제, 안전성 학습, 레드팀 테스트로 줄이지만 완전히 없애기는 어렵다 |
| **할루시네이션** | 존재하지 않는 사실, 잘못된 수치, 가짜 출처를 확실한 것처럼 만든다. 교육·의료·법률·금융·채용처럼 사람에게 큰 영향을 주는 영역에서는 사람이 최종 판단해야 한다 |

## LangChain

![LangChain](/images/llm/fig-langchain-logo.png)

[LangChain](https://www.langchain.com/)은 LLM 기반 애플리케이션과 에이전트를 쉽게 개발하도록 돕는 오픈소스 프레임워크다. 실제 서비스는 모델을 한 번 호출하는 것만으로는 부족하고, LLM 호출 앞뒤로 여러 기능이 필요하다.

- 사용자의 질문을 프롬프트로 구조화하기
- OpenAI, Anthropic, Google Gemini, Ollama 등 다양한 모델 연결하기
- 검색 시스템, 데이터베이스, API, 파일, 웹 검색 도구와 연결하기
- 이전 대화 내용 기억하기
- 모델 출력을 JSON 같은 구조화된 형식으로 받기
- 에이전트가 상황에 따라 도구를 고르고 반복 작업하게 만들기
- 실행 중 오류를 디버깅하고 평가하기

2022년 Harrison Chase가 오픈소스로 시작했고, 2024년 1월 첫 안정 버전 v0.1, 2025년 10월 v1.0이 나오면서 에이전트 개발용 구조로 정리되었다.

### LLM 애플리케이션이 다른 점

일반 프로그램은 같은 입력에 같은 절차로 같은 결과를 낸다. LLM 애플리케이션은 응답이 확률적이고, 입력이 매우 다양하고, 외부 도구를 호출하거나 여러 단계를 거쳐야 한다. "우리 회사 휴가 규정 알려줘"에 답하려면 질문만 LLM에 넘겨서는 안 되고 규정 문서를 찾아서 함께 넘겨야 한다.

```text
사용자 질문 → 질문 분석 → 관련 문서 검색 → 검색 결과를 프롬프트에 삽입 → LLM 호출 → 답변 생성 → 출력 형식 정리
```

```python
# llm이 다른 어플과 다른 특징
# 같은 입력이어도 다른 답
# 입력이 다양함
# 외부도구도 호출해야 함
```

```python

```

## LangChain의 주요 구성 요소

| 구성 요소 | 하는 일 | 이 시리즈 |
|---|---|---|
| **Model** | 실제 LLM 호출. 여러 제공자의 모델을 공통 방식으로 쓴다 | 2편 |
| **Prompt** | LLM에 전달하는 지시문. 역할, 답변 형식, 참고 문서, 제약 조건을 질문과 함께 넣는다. 템플릿으로 만들고 실행 때 값을 채운다 | 3편 |
| **Chain** | 프롬프트 생성 → 모델 호출 → 출력 파싱처럼 여러 단계를 연결한 실행 흐름(workflow). **LCEL**로 구현한다 | 5편 |
| **Tool** | LLM이 쓸 수 있는 외부 기능(웹 검색, DB 조회, 계산기, 코드 실행, 사내 API, 벡터 DB 검색). LLM이 뇌라면 Tool은 팔다리다 | Agent 묶음 |
| **Retrieval** | 질문과 관련된 정보를 외부 문서·DB에서 찾아온다. 문서 로더, 텍스트 분할기, 임베딩, 벡터 스토어, 리트리버로 RAG를 만든다 | RAG 묶음 |
| **Memory** | 이전 대화를 기억한다. LLM 호출은 독립적이라 대화 이력을 저장했다가 다음 호출에 넣어 준다 | Agent 묶음 |
| **Agent** | 목표를 위해 여러 단계를 수행한다. **목표 달성 여부를 LLM이 판단**하고 계속할지 멈출지 정한다 | Agent 묶음 |

## LangChain 생태계

![LangChain 생태계](/images/llm/fig-langchain-ecosystem.png)

| 도구 | 역할 | 비유 |
|---|---|---|
| **LangChain** | LLM 애플리케이션과 에이전트 **개발 프레임워크**. 모델 호출 추상화, 프롬프트, 도구 연결, 구조화된 출력, RAG, 에이전트 생성, 외부 서비스 통합(Integrations)을 제공한다 | 빠르게 만들기 |
| **LangGraph** | 복잡한 에이전트 흐름을 제어하는 상태 기반 **에이전트 오케스트레이션 프레임워크**. 분기, 반복, 상태 저장, 사람의 승인 절차를 그래프로 정의한다 | 정교하게 제어하기 |
| **LangSmith** | 실행 추적, 디버깅, 평가, 배포, 모니터링 **플랫폼** | 관찰하고 개선하기 |

```python

# 랭체인
# => 어플리케이션을 만드는 라이브러리(개발자의 커스텀이 쉽게 가능함)
# Rag 기반의 질의응답을 시스템을 만들때
# 랭체인을 가지고 간단한 ai agent를 만들수있음

# 랭그래프
# 복잡한 ai agent를 만들 때
# 정교하게 제어가능함

# 인그레이션
# => 외부시스템이랑 연결해줌 (ex. gpt, claude)


# 랭그래프 플랫폼=> 서비스해주는 서버


# 랭스미스 => (커머셜) . agent를 관찰하고 평가하고 개선하기 위한 플랫폼
```

메모의 "인그레이션"은 **Integrations**다. `langchain-openai`, `langchain-anthropic`, `langchain-qdrant`처럼 외부 서비스마다 연결 패키지가 따로 있고, LangChain 본체는 이것들을 같은 인터페이스로 묶는다.

LangGraph가 필요한 예로, 고객 지원 에이전트는 이런 흐름을 가진다.

```text
문의 접수
   ↓
문의 유형 분류
   ↓
주문 관련 문의인가?
   ├─ 예: 주문 DB 조회
   └─ 아니오: 일반 FAQ 검색
   ↓
답변 초안 생성
   ↓
위험한 작업인가?
   ├─ 예: 담당자 승인 요청
   └─ 아니오: 사용자에게 답변
```

분기와 승인 절차가 있어서 순서대로 이어 붙이는 Chain으로는 만들기 어렵다.

LangSmith는 챗봇이 이상한 답을 했을 때 원인을 찾는 도구다. 원래 질문, 모델에 실제로 전달된 프롬프트, 검색된 문서, 호출한 도구와 그 결과, 잘못 판단한 단계, 비용과 응답 시간, 이전 버전 대비 성능을 추적한다.

## LangChain vs LangGraph, 언제 무엇을

| 상황 | 추천 |
|---|---|
| 간단한 챗봇, 문서 질의응답(RAG), 빠른 프로토타입 | LangChain |
| 모델 제공자를 바꿀 가능성이 있다 | LangChain (같은 인터페이스) |
| 도구 몇 개를 붙인 간단한 에이전트 | LangChain (`create_agent`) |
| 조건 분기·반복이 많고, 중간 상태를 저장해야 한다 | LangGraph |
| 사람의 승인 후 다음 단계로 가야 한다, 오래 걸리는 작업 | LangGraph |
| 답변이 왜 이상한지 추적하고, 프롬프트 버전별로 성능을 비교하고 싶다 | LangSmith (둘 다와 함께 쓴다) |

## 정리

- **LLM**은 대규모 파라미터를 대규모 데이터로 학습해 다음 토큰을 예측하는 범용(파운데이션) 모델이다. 사실 DB가 아니라서 할루시네이션이 생기고, 그래서 **검증과 근거 설계**가 중요하다
- 활용 방식은 **프롬프트 엔지니어링(2022~23) → RAG·추론 모델(2024) → Tool Calling·Agent·컨텍스트 엔지니어링(2025~)**으로 옮겨 왔다
- 한국어는 토큰을 더 많이 써서 비용이 크다. 반복되는 시스템 프롬프트는 영어로 쓰면 아낄 수 있다
- 오픈소스 LLM은 가중치를 받아 직접 돌리고, 상용 LLM은 API로 쓴다
- **LangChain**은 제공사마다 다른 LLM 라이브러리를 같은 인터페이스로 묶고, Model·Prompt·Chain·Tool·Retrieval·Memory·Agent 구성 요소를 제공한다
- 복잡한 흐름은 **LangGraph**, 추적과 평가는 **LangSmith**가 맡는다
