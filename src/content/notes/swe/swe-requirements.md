## 요구사항 분석이란

요구사항 분석은 개발 초기에 **사용자와 이해관계자의 요구를 수집하고, 명확히 정의하고, 문서화하는 과정**이다. 목적은 두 가지다.

- 사용자가 기대하는 것을 정확히 이해해 결과물에 반영한다.
- 개발 중 "이게 아니었는데" 하는 혼란과 변경을 줄인다.

| 과정 | 내용 |
|---|---|
| 수집 | 인터뷰·설문·워크샵 등으로 요구를 모은다 |
| 명세 | 모은 요구를 구체적으로 문서화한다 |
| 검증 | 일관되고 완전하며 실현 가능한지 검토한다 |
| 관리 | 변경을 추적하고 프로젝트 끝까지 반영되게 관리한다 |

산출물은 **요구사항 명세서(SRS)** 와 **요구사항 추적 매트릭스(RTM)** 다.

> **보충**: 요구사항이 늦게 바뀔수록 비용이 커진다. 기획 단계의 문장 한 줄 수정이 개발 후에는 화면·DB·테스트를 모두 고치는 일이 된다. 요구사항 분석에 시간을 쓰는 이유가 이것이다.

## 요구사항 수집 기법

| 기법 | 방법 | 장점 | 단점 |
|---|---|---|---|
| 인터뷰 | 사용자와 일대일 대화 | 깊이 있는 정보 | 시간·비용, 인터뷰어 역량에 좌우 |
| 설문조사 | 다수에게 질문지 | 많은 사람에게 빠르게 | 낮은 응답률, 깊이 부족 |
| 워크샵 | 이해관계자 집단 토론 | 다양한 관점, 합의 도출 | 일정 조율, 참여 편차 |
| 관찰 | 실제 업무 현장 관찰 | **말로 못 하는 요구** 발견 | 관찰자 주관, 시간 소요 |
| 포커스 그룹 | 특정 주제로 사용자 토론 | 아이디어를 한 번에 | 일부 의견 과대 반영 |
| 브레인스토밍 | 자유로운 아이디어 발상 | 창의적 아이디어, 팀 참여 | 실현성 낮은 아이디어 다수 |

기법 선택 기준은 프로젝트 규모(클수록 여러 기법 병행), 이해관계자 접근성(가까우면 인터뷰·워크샵), 예산과 시간이다.

관찰이 특히 중요하다. 사용자는 이미 익숙해진 불편은 말하지 않는다. 엑셀을 매일 손으로 복사하는 사람은 "자동화가 필요하다"고 말하지 않고 그냥 복사한다. 그 장면을 봐야 요구가 보인다.

## 요구사항 명세서(SRS)

SRS(Software Requirements Specification)는 시스템의 기능적·비기능적 요구사항과 제약조건을 정리한 문서로, 이해관계자의 소통 기준이자 개발의 기준이 된다. **정해진 표준 양식은 없고** 회사마다 자기 양식이 있다. 보통 개요(목적·범위·용어 정의)와 요구사항 목록으로 구성한다.

### 기능과 비기능

| | 기능 요구사항 | 비기능 요구사항 |
|---|---|---|
| 정의 | 시스템이 **무엇을 하는가** | 시스템이 **얼마나 잘 하는가**(품질 속성) |
| 예 | 로그인, 보고서 생성 | 응답 시간, 보안, 사용성, 동시 접속 |
| 검증 | 기능이 동작하는가 | 수치·기준을 만족하는가 |

### 항목

| 항목 | 내용 |
|---|---|
| 요구사항 ID | 고유 번호(`REQ-001`). 추적·관리에 사용 |
| 요구사항명 | 짧은 이름 |
| 요구사항 내용 | 구체적인 설명 |
| 중요도 | 목적과의 관련성, 우선순위(상·중·하) |
| 진행사항 | 미진행 / 진행중 / 완료 / 다음 버전 |
| 수용 여부 | 수용 / 검토중 / 미수용 |

### 작성 원칙

| 원칙 | 의미 |
|---|---|
| 명확성 | 이해하기 쉽게. **요구사항 하나에 내용 하나** |
| 완전성 | 필요한 기능과 조건을 빠짐없이 |
| 일관성 | 요구사항끼리 모순·중복 없이, 용어도 통일 |
| 검증 가능성 | 테스트로 확인할 수 있게 **측정 가능한 기준** 제시 |
| 추적 가능성 | 개발 과정 내내 추적할 수 있게 |

검증 가능성이 가장 자주 무너진다. "빠르게 로딩되어야 한다"는 테스트할 수 없다. 강의 예시의 "페이지 로딩 시간이 3초 이내", "초당 1000명 동시 접속 처리"처럼 숫자로 쓴다.

강의 자료의 쇼핑몰 SRS 예시 일부다.

| 요구사항ID | 기능유형 | 요구사항명 | 요구사항 내용 | 중요도 | 수용여부 |
|---|---|---|---|---|---|
| REQ-001 | 기능 | 상품 검색 | 사용자가 키워드, 카테고리, 가격 범위로 상품을 검색할 수 있어야 함 | 상 | 수용 |
| REQ-004 | 기능 | 회원 관리 | 회원 가입, 로그인, 정보 수정, 탈퇴 기능을 제공해야 함 | 중 | 수용 |
| REQ-007 | 비기능 | 보안 | HTTPS를 사용하고 개인정보를 암호화하여 저장해야 함 | 상 | 수용 |
| REQ-008 | 비기능 | 성능 | 페이지 로딩 시간이 3초 이내여야 함 | 중 | 검토중 |

REQ-004는 "하나에 하나" 원칙으로 보면 네 개(가입·로그인·수정·탈퇴)로 쪼개는 편이 낫다. 넷의 진행 상황과 테스트가 따로 움직이기 때문이다.

## 요구사항 추적 매트릭스(RTM)

RTM(Requirements Traceability Matrix)은 요구사항 하나가 **설계·구현·테스트의 어디에 반영됐는지** 연결한 표다. "이 요구사항은 어느 화면, 어느 코드, 어느 테스트가 담당하나"와 반대로 "이 테스트는 어느 요구사항을 확인하나"를 양쪽에서 찾을 수 있게 한다. 요구사항이 바뀌었을 때 고쳐야 할 곳을 빠짐없이 찾는 도구다. 아래 `mypoll` 명세서의 오른쪽 세 칸이 간단한 RTM 역할을 한다.

## 예시: mypoll 요구사항 명세서

[Django 시리즈](/notes/django/django-getting-started)의 설문 프로젝트를 요구사항으로 다시 써 봤다. 진행사항은 실제 코드 기준이다.

**개요**: 회원이 설문을 만들고 누구나 투표·결과를 볼 수 있는 웹 설문 서비스. LLM 채팅 기능을 함께 제공한다.

| ID | 유형 | 요구사항명 | 요구사항 내용 | 중요도 | 진행 | 구현(View) | 테스트 |
|---|---|---|---|---|---|---|---|
| REQ-001 | 기능 | 설문 목록 | 등록된 설문을 최신순으로 10개씩 페이지로 나누어 보여 준다 | 상 | 완료 | `vote_list` | TC-01~03 |
| REQ-002 | 기능 | 투표 | 설문의 보기 하나를 골라 투표한다 | 상 | 완료 | `vote_form`, `vote` | TC-04~06 |
| REQ-003 | 기능 | 중복 투표 방지 | 같은 사용자는 한 설문에 한 번만 투표한다 | 상 | 완료(쿠키) | `vote` | TC-07 |
| REQ-004 | 기능 | 결과 조회 | 보기별 득표 수를 보여 준다 | 상 | 완료 | `vote_result` | TC-08 |
| REQ-005 | 기능 | 설문 등록 | 로그인한 회원이 질문 1개와 보기 2개 이상을 등록한다 | 상 | 완료 | `vote_create` | TC-09~12 |
| REQ-006 | 기능 | 회원 가입 | 아이디·비밀번호·이름·이메일·생일로 가입한다 | 중 | 완료 | `create` | TC-13~14 |
| REQ-007 | 기능 | 로그인·로그아웃 | 로그인 후 원래 요청한 페이지로 이동한다 | 중 | 완료 | `user_login` | TC-15~17 |
| REQ-008 | 기능 | 정보 수정·비밀번호 변경·탈퇴 | 회원이 자기 정보를 관리한다 | 중 | 완료 | `update` 외 | - |
| REQ-009 | 기능 | AI 채팅 | 질문에 대한 LLM 답변을 실시간으로 표시하고 대화 맥락을 유지한다 | 중 | 완료 | `stream_chat` | TC-18 |
| REQ-010 | 비기능 | 보안 | 비밀번호는 해시로 저장하고, 상태를 바꾸는 요청은 POST + CSRF 토큰을 요구한다 | 상 | 일부 | 전역 | TC-19 |
| REQ-011 | 비기능 | 성능 | 채팅 첫 글자가 질문 후 3초 안에 표시된다 | 중 | 미측정 | - | - |
| REQ-012 | 비기능 | 가용성 | 서버 재부팅 후 서비스가 자동으로 다시 시작된다 | 중 | 일부 | systemd | - |

작성하면서 드러난 것들이 있다.

- **REQ-003의 "같은 사용자"가 모호하다.** 구현은 브라우저 쿠키라 브라우저를 바꾸면 다시 투표할 수 있다. 요구사항을 "로그인한 회원 기준 1회"로 정했다면 지금 구현은 요구를 만족하지 못한다. 요구사항이 모호하면 구현이 편한 쪽으로 해석된다.
- **REQ-010이 "일부"인 이유**는 [Django 6편](/notes/django/django-auth)에서 본 로그아웃 GET 요청과 `next` 열린 리다이렉트 때문이다.
- **REQ-012가 "일부"인 이유**는 [AWS 4편](/notes/aws/aws-django-deploy)의 `RuntimeDirectory` 불일치로 재부팅 후 서비스가 실패할 수 있기 때문이다.
- REQ-011은 "빠르게"가 아니라 "3초"로 써 두었기 때문에 **미측정**이라고 말할 수 있다. 측정 기준이 없으면 완료인지조차 판단할 수 없다.

테스트 칸의 TC 번호는 [4편](/notes/swe/swe-test-architecture)의 테스트 케이스와 이어진다.

## 정리

| 개념 | 핵심 |
|---|---|
| 요구사항 분석 | 수집 → 명세 → 검증 → 관리 |
| 수집 기법 | 인터뷰, 설문, 워크샵, 관찰, 포커스 그룹, 브레인스토밍 |
| SRS | 기능·비기능을 나눠 ID·이름·내용·중요도·진행·수용 여부로 정리 |
| 작성 원칙 | 명확(하나에 하나), 완전, 일관, **검증 가능(숫자)**, 추적 가능 |
| RTM | 요구사항 ↔ 설계·구현·테스트 연결 |

다음 글에서는 요구사항을 사용자 관점의 시나리오로 풀어 쓰는 유즈케이스를 다룬다.
