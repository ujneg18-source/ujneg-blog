## 유즈케이스란

유즈케이스는 **사용자(액터)가 원하는 일을 달성하기 위해 시스템이 제공하는 시나리오**다. 이 시스템을 **누가, 왜, 어떤 순서로** 쓰는지를 사용자 관점에서 정리한, 일종의 "사용자 관점의 기능 설명서"다.

| 목적 | 내용 |
|---|---|
| 요구사항 명확화 | 기능을 구체적인 흐름으로 써서 사용자와 개발자가 같은 이해를 갖게 함 |
| 개발 지원 | 설계·개발·테스트의 기준 자료 |
| 커뮤니케이션 | 개발자·디자이너·테스터·기획자 공통 언어 |
| 테스트 케이스 작성 | 흐름 하나하나가 테스트 케이스의 출발점 |

마지막 항목이 실무적으로 가장 쓸모 있다. 유즈케이스의 대체·예외 흐름을 쓰다 보면 테스트할 상황이 저절로 목록이 된다.

## 구성 요소

| 요소 | 내용 |
|---|---|
| 유즈케이스 | 액터가 시스템으로 달성하려는 목표(동사구: "투표하기") |
| 액터 | 시스템을 사용하는 **외부** 주체. 사람(사용자, 관리자) 또는 시스템(결제 API, 인증 서버) |
| 사전 조건 | 시작 전에 참이어야 하는 상태 |
| 사후 조건 | 끝난 뒤 보장되는 상태 |
| 주요 흐름(Main) | 정상적으로 진행되는 기본 시나리오 |
| 대체 흐름(Alternative) | 다른 선택을 했을 때의 정상 시나리오 |
| 예외 흐름(Exception) | 에러·예외 상황의 흐름 |

대체 흐름과 예외 흐름은 번호로 주요 흐름에 매단다. `4a`는 "주요 흐름 4단계에서 갈라지는 a번째 경우"다.

> **보충**: 액터는 "시스템 바깥"에 있어야 한다. 결제 기능에서 우리 서버가 부르는 외부 결제사(PG) 시스템은 액터이고, 우리 서버 안의 결제 모듈은 액터가 아니다. 액터를 정하는 일이 곧 **시스템의 경계**를 정하는 일이다.

## 산출물

| 산출물 | 내용 |
|---|---|
| 유즈케이스 명세서 | 유즈케이스마다 액터에서 시작하는 흐름을 문서로 작성 |
| 유즈케이스 다이어그램 | 액터(사람 모양)와 유즈케이스(타원)를 시스템 경계(사각형) 안팎에 두고 선으로 연결 |
| 시나리오 | 특정 사례 한 가지를 처음부터 끝까지 서술 |

## 강의 예시: 로그인

```text
유즈케이스 이름: 로그인
목적: 사용자가 시스템에 접근하기 위해 로그인한다.
주요 행위자: 사용자
사전 조건: 사용자는 유효한 사용자 계정과 비밀번호를 가지고 있어야 한다.
사후 조건: 사용자는 시스템에 로그인되어 있으며, 메인 화면으로 이동된다.

주요 흐름:
  1. 사용자는 로그인 페이지를 연다.
  2. 사용자는 사용자 이름과 비밀번호를 입력한다.
  3. 사용자는 '로그인' 버튼을 클릭한다.
  4. 시스템은 사용자 이름과 비밀번호를 검증한다.
  5. 시스템은 사용자를 메인 화면으로 이동시킨다.

대체 흐름:
  2a. 비밀번호 찾기: 비밀번호를 잊어버린 경우 '비밀번호 찾기'로 재설정을 진행한다.

예외 흐름:
  4a. 로그인 실패: 사용자 이름이나 비밀번호가 유효하지 않으면 오류 메시지를 표시하고 로그인 페이지에 머무른다.

특별 요구사항:
  - 로그인 시도는 보안 이유로 5회 실패 시 일시적으로 계정이 잠긴다.
```

"특별 요구사항"은 흐름으로 표현하기 어려운 비기능 요구사항(보안·성능)을 적는 칸이다. 강의 자료의 결제 처리 예시는 외부 **결제 시스템**이 두 번째 액터로 등장하고, "결제 정보는 SSL로 암호화", "결제 과정은 3초 이내" 같은 특별 요구사항이 붙는다.

## 예시: 설문 프로젝트의 유즈케이스

### 다이어그램

```text
                ┌──────────── mypoll ─────────────┐
                │                                  │
  방문자 ───────┼──── (설문 목록 보기)             │
     │          │──── (투표하기) ────<<include>>── (결과 보기)
     │          │──── (회원 가입)                  │
     △          │                                  │
  회원 ─────────┼──── (설문 등록하기)              │
                │──── (로그인 / 로그아웃)          │
                │──── (AI 채팅) ──────────────────┼──── OpenAI API
                │                                  │      (시스템 액터)
  관리자 ───────┼──── (설문·회원 관리[admin])      │
                └──────────────────────────────────┘
```

- `회원 △ 방문자`: 회원은 방문자가 할 수 있는 일을 모두 할 수 있다(액터 상속).
- `<<include>>`: 투표하기는 항상 결과 보기로 이어진다(투표 후 결과 화면으로 redirect).
- OpenAI API는 우리 시스템 밖에 있으므로 **시스템 액터**로 그렸다.

### 투표하기

[Django 3편](/notes/django/django-polls-views)의 `vote_form`·`vote`·`vote_result` 동작을 그대로 옮겼다.

```text
유즈케이스 이름: 투표하기 (REQ-002, REQ-003)
목적: 방문자가 설문의 보기 하나를 골라 투표하고 결과를 확인한다.
주요 행위자: 방문자
사전 조건: 보기가 2개 이상 등록된 설문이 있다.
사후 조건: 선택한 보기의 득표 수가 1 증가하고, 이 설문에 투표했다는 기록이 브라우저에 남는다.

주요 흐름:
  1. 방문자는 설문 목록에서 설문을 선택한다.
  2. 시스템은 질문과 보기 목록을 보여 준다.
  3. 방문자는 보기 하나를 선택하고 '투표'를 누른다.
  4. 시스템은 이 설문에 이미 투표했는지 확인한다.
  5. 시스템은 선택한 보기의 득표 수를 1 증가시킨다.
  6. 시스템은 투표 기록을 저장하고 결과 화면으로 이동시킨다.
  7. 방문자는 보기별 득표 수를 확인한다.

대체 흐름:
  3a. '선택해제'를 누르면 선택이 초기화되고 2단계로 돌아간다.
  3b. '목록으로'를 누르면 설문 목록으로 이동한다.

예외 흐름:
  1a. 없는 설문 번호로 접근하면 "없는 질문입니다" 오류 화면을 보여 준다.
  3c. 보기를 선택하지 않고 투표하면 "보기를 선택해주세요." 메시지와 함께 2단계 화면에 머무른다.
  4a. 이미 투표한 설문이면 "이미 투표한 질문입니다." 메시지와 함께 2단계 화면에 머무르고 득표 수는 바뀌지 않는다.

특별 요구사항:
  - 투표 후 새로고침해도 표가 다시 올라가지 않아야 한다(POST 후 redirect).
```

이렇게 쓰고 나서 실제 동작과 대조하면 명세와 구현이 어긋나는 곳이 보인다.

- **사후 조건 "투표 기록이 브라우저에 남는다"**: 구현은 만료 시간 없는 쿠키라 **브라우저를 닫으면 기록이 사라진다**(Django 3편). 명세에 "7일간 유지"처럼 기간을 적었다면 바로 불일치로 드러났을 것이다.
- **예외 1a**: 오류 화면은 나오지만 HTTP 상태 코드는 200이다. 명세에 상태 코드까지 적지는 않으므로 유즈케이스로는 통과, 테스트 단계에서 잡을 일이다.
- **명세에 없는 흐름**: 개발자 도구로 다른 설문의 보기 번호를 보내면 그 보기에 표가 올라간다. 사용자 관점의 유즈케이스로는 드러나지 않는 경로라, 보안 관점의 테스트가 따로 필요하다.

### 설문 등록하기

```text
유즈케이스 이름: 설문 등록하기 (REQ-005)
목적: 회원이 새 설문(질문 1개, 보기 2개 이상)을 등록한다.
주요 행위자: 회원
사전 조건: 회원이 로그인되어 있다.
사후 조건: 질문과 보기가 함께 저장되고 설문 목록 맨 앞에 나타난다.

주요 흐름:
  1. 회원은 '설문등록' 메뉴를 선택한다.
  2. 시스템은 질문 입력칸 1개와 보기 입력칸 2개를 보여 준다.
  3. 회원은 질문과 보기를 입력하고 '등록'을 누른다.
  4. 시스템은 입력값을 검증한다.
  5. 시스템은 질문과 보기를 하나의 작업으로 저장한다.
  6. 시스템은 설문 목록으로 이동시킨다.

대체 흐름:
  2a. '보기 추가'를 누르면 보기 입력칸이 하나 늘어난다.
  2b. '보기 삭제'를 누르면 마지막 보기 입력칸이 지워진다(최소 2개 유지).

예외 흐름:
  1a. 로그인하지 않은 상태면 로그인 화면으로 이동하고, 로그인 후 등록 화면으로 돌아온다.
  4a. 질문이 5글자 미만이면 "질문은 5글자 이상 입력하세요." 메시지와 함께 입력값을 유지한 채 2단계에 머무른다.
  4b. 내용 있는 보기가 2개 미만이면 오류 메시지와 함께 2단계에 머무른다.
  5a. 저장 중 오류가 나면 아무것도 저장하지 않고 오류 화면을 보여 준다.
```

이 명세를 실제 동작과 맞춰 보면 [Django 4편](/notes/django/django-form-formset)의 버그가 그대로 걸린다.

| 흐름 | 명세 | 실제 |
|---|---|---|
| 2a 보기 추가 | 입력칸이 늘고 저장된다 | 칸은 생기지만 `TOTAL_FORMS`가 안 늘어 **추가한 보기가 저장되지 않음** |
| 4b 보기 부족 | 오류 메시지 | 보기 칸을 비우면 **500 서버 에러**(`KeyError`) |
| 5a 저장 오류 | 오류 화면 | 오류 화면은 나오지만 메시지가 빈칸(context 키 불일치) |

코드를 먼저 보면 "동작하는 것 같다"로 끝나기 쉽다. 사용자 관점의 흐름을 먼저 적고 하나씩 눌러 보면 빠진 경우가 드러난다. 유즈케이스가 테스트 케이스의 출발점이라는 말이 이 뜻이다.

## 정리

| 개념 | 핵심 |
|---|---|
| 유즈케이스 | 액터가 목표를 달성하는 시나리오. 누가·왜·어떤 순서로 |
| 액터 | 시스템 바깥의 사람 또는 시스템. 액터 = 시스템 경계 |
| 사전·사후 조건 | 시작 전 상태 / 끝난 후 보장되는 상태 |
| 주요·대체·예외 흐름 | 기본 / 다른 선택 / 오류. `4a`처럼 주요 흐름 단계에 매단다 |
| 특별 요구사항 | 흐름으로 못 쓰는 보안·성능 조건 |

- 예외 흐름을 빠짐없이 쓰는 것이 유즈케이스의 핵심이고, 그 목록이 그대로 테스트 케이스가 된다.
